# Design

High level notes on the software design

### Tools used

pgx/v5 - PostgreSQL driver \
pgxpool - Connection pool, built on pgx \
sqlc - Generates type-safe idiomatic Go code from SQL \
goose - Migration system

## Database creation

### PostgreSQL DB creation
- `dbmigrate/main.go` is the CLI, implements `up, down, status, version` and uses Goose to applies the database migrations.
- `db/migrations/embed.go` essentially ensures that all the migration related SQL files are embedded into the executable. The executable does not need to rely on the migration SQL files residing somewhere on local disk.
- `db/migrations/*.sql` are the migrations
- `db/queries/*.sql` are the queries

### PostgreSQL schema

- `db/migrations/00001_initial_schema.sql`: Essentially 3 tables - `jobs, job_chain_associations, chunks`, and some indexes

## Database querying

Overall path:
API ->
-> Go functions in `internal/postgres` which wrap around ->
-> SQLC generated Go functions (`interal/postgres/db`) of the SQL queries ->
-> `pgx/pgxpool` which goes to the PostgreDB instance

### PostgreSQL queries (`db/queries/*.sql`)

#### jobs.sql
Pretty straightforward overall
- Job state change to `SUCCEEDED/FAILED` is checked on the 2 queries: `RecordJobChunkSucceeded/Failed`

#### chains.sql
- `LockChainAssociations`: Takes in 2 arrays, rank_id and chain_id, zips them as pairs and locks those rows.
- `ListDrainingChainAssociations` looks strange, it filters `job_chain_associations` entries that are `DRAINING` and is used for cleanup. The params are just so that it can break the cleanup loop into sections

#### chunks.sql
- `FindClaimCandidates` is the main query to find usable chunks to process. It filters chunks where state is READY and is past the `not_before` time or chunks where state is LEASED but lease is expired (`lease_expires_at`) 
- `FindExpiredDrainingChunkIDs,RequeueExpiredDrainingChunks` are queries for reconciliation, finding and requeueing expired chunks associated with draining chains.

### SQLC generated files
The SQLC generated files are in `internal/postgres/db/*.sql.go`. Each generated file corresponds with one query file in `db/queries/`. Don't have to read thse files and should NOT edit them. But some broad points are as follows
- Generally, for each query, there will be:
- input param type, e.g. `GetChunksParams`, which is a struct of the params
- const \[query-name\], which is just the same SQL query in a string with the variables put in as $1, $2 etc.
- Go function to actually carry out the query 

The files `internal/postgres/dbdb.go,doc.go,models.go` are also generated by SQLC

#### db.go
It's a small file, but has interesting semantics
- The `type DBTX interface` allows different `pgx` types, like `pgx.Tx, *pgx.Conn, *pgxpool.Pool` as long as they implement the same 3 function signatures
- The `type Queries struct` just wrap one of the DBTX instances and then attach all the query Go functions as methods on the `Queries` class. (You can see this in the generated query files)
- Calling `db.New` invokes the function in this file, which basically takes a DBTX instance and returns a `Queries` instance

### Actual Go functions

#### store.go
Common store infrastructure. Defines a key `Store` struct that contains the `pgxpool.Pool` and other database access related settings like max claim chunks, max renew leases.
- A more important function is `withTransaction` which essentially obtains a connection from the pool and allow all the queries associated with one transaction to occur as part of the same connection, with commit / rollback
- Throughout the handwritten Go codes, you will see `withTransaction` used to wrap full functions that make multiple queries
